## Сервер: остановка и запуск

Все команды — из каталога проекта на сервере (`cd /srv/test-knt`), там лежит
`docker-compose.yml`. Сервисов пять: `db`, `redis`, `web`, `worker`, `bot`.

Остановить сайт, оставив контейнеры на месте (быстрее всего поднять обратно):

```docker compose stop```

Поднять снова:

```docker compose start```

Полная остановка — контейнеры удаляются, база и файлы остаются (том `pgdata` цел):

```docker compose down```

Поднять после `down` (или впервые):

```docker compose up -d```

**Никогда не `docker compose down -v`** — флаг сносит тома вместе с базой.

Выкатить новый код: сначала `git pull`, потом пересборка образа и перезапуск.
Миграции и `collectstatic` прогоняет сам контейнер `web` при старте (см. `entrypoint.sh`),
руками их дёргать не надо.

```docker compose up -d --build```

Перезапустить один сервис (например, после правки `.env`):

```docker compose restart web```

Что происходит сейчас и логи:

```docker compose ps```

```docker compose logs -f --tail=100 web```

Разовая команда внутри контейнера:

```docker compose exec web python manage.py <команда>```

Порядок важен только при первом запуске: `web` ждёт готовности `db` и `redis` сам
(healthcheck в compose). У `worker` и `bot` entrypoint переопределён, поэтому миграции
они не накатывают — это делает только `web`, и двое одновременно за них не дерутся.

## Файлы: как они раздаются

Всё, что загружают люди — файлы книг и материалов, картинки галереи и комментариев,
аватары, — лежит в одном бакете R2, а раздаётся **с нашего сервера**, с домена
`files.inbicst.ru`. Cloudflare в пути браузера нет.

```
браузер ─► files.inbicst.ru/img/<подпись>/ ─► Django: проверил подпись, вернул
                                              ТОЛЬКО заголовок X-Accel-Redirect
                                           ─► nginx: кеш на диске
                                           ─► промах: сходил в R2, один раз навсегда
```

Байты через python не идут никогда — иначе воркер gunicorn держался бы всё скачивание.
Кеш неограниченно долгий: объект по ключу неизменен (в ключе uuid, перезапись запрещена),
так что протухать нечему. Конфиг — в `nginx.conf` и `nginx-accel.conf`.

Отдельный хост, а не путь на сайте, — это другой origin: куки сессии туда не уходят,
и файл, проскочивший мимо фильтра расширений, не дотянется до страниц сайта. Плата за
это — на `files.` нет сессии, поэтому разрешением служит подпись в самом адресе.
Перебрать библиотеку всё равно нельзя: токен подписан `SECRET_KEY`, в ключе uuid
(`attachments.storage.random_key`), листинг бакета закрыт.

### Почему не свой домен на самом R2

Пробовали, не работает. Домен R2 обязан быть проксирован через Cloudflare, а Cloudflare
с 9 июня 2025 душат российские провайдеры: проходят первые ~16 КБ, дальше поток
обрывается. Проверено подменой адресов — с того же IP посторонний хост качается за 0.8 с,
а `files.inbicst.ru` на любом IP Cloudflare умирает на 24 КБ; различается только имя в SNI.
Перевести запись R2 в **DNS only** нельзя: она управляемая, у бакета нет origin-IP.

Работающий сейчас `*.r2.cloudflarestorage.com` (туда ходит наш nginx) в список пока
не попал. Если попадёт — переезд на другое S3-совместимое хранилище стоит замены ключей
в `.env`: код ходит через `S3Storage`.

### Переключение хранилища

`R2_BUCKET` пуст — файлы ложатся в `media/` на диске; заполнен — в R2. Адреса снаружи
при этом одинаковые, меняется только внутренний переход (`/__local/` вместо `/__r2/`).
Разработка живёт на локальном диске: в сеть не ходим, боевой бакет не трогаем.

Прямая загрузка крупных файлов в обход приложения работает **только при включённом R2**
(`attachments.uploads.direct_upload`). Проверять её локально — временно заполнив ключи.

Полной копии бакета на диске мы не держим. Если файлы приехали не в то хранилище
(например, загружали, пока R2 лежал), их догоняют вручную:

```python manage.py storage_sync --check```

```python manage.py storage_sync --push --apply```

`--push` льёт с диска в R2, `--pull` — обратно. Без `--apply` только показывает.

### Старые файлы

Загруженные до перехода на uuid лежат по предсказуемым путям вида
`books/12/files/Зорич.pdf`. Разово перевести их на ключи с uuid:

```python manage.py rekey_media --apply```

Без `--apply` только показывает. Новые загрузки приходят с uuid сразу.

## Фоновые задачи (Celery)

Очереди нужен Redis. Локально — контейнером:

```docker run -d --name knt-redis -p 127.0.0.1:6379:6379 redis:8-alpine redis-server --save "" --appendonly no```

Воркер. На Windows обязателен `--pool=solo`: обычный prefork форкает процесс, а Windows этого не умеет.

```.\.venv\Scripts\celery.exe -A knt worker -l info --pool=solo```

Проверка всей связки «сайт → Redis → воркер»:

```python manage.py celery_check```

В проде воркер поднимается сервисом `worker` из docker-compose, Redis там уже есть.
Базы Redis разведены: 0 — шина чата, 1 — очередь задач, 2 — ответы задач.

Письма тоже идут очередью, поэтому в разработке они печатаются **в окне воркера**, а не
сервера. Если воркер не запущен, письмо просто ждёт в очереди; если лежит сам Redis —
уходит напрямую, без очереди.
