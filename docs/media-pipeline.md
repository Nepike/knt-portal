# Конвейер тяжёлой медиа: пекарня и приёмка

Договор о том, как на сайт попадают видеофайлы — фоны профиля, шапки и лекции.
Решено 25 авг 2026. **Заменяет** ту часть `PLAN.md`, где GPU-воркер сидел на WireGuard
и слушал очередь Celery: воркер больше не сервер, ему не нужен ни белый адрес, ни
входящий доступ.

## Принцип

> **Сайт не конвертирует. Сайт принимает по спеке и отказывает с внятной причиной.**

На сервере-хостинге нет и не будет `ffmpeg`. Он отдаёт страницы, ведёт базу и раздаёт
ссылки; байты видео не проходят через python ни на загрузке, ни на раздаче.

Три причины: перекодировка часовой лекции займёт часы и положит машину, которая
одновременно обслуживает 500 человек; тяжёлая зависимость в образе не нужна ради
операции, случающейся раз в неделю; а качество и скорость всё равно упираются
в видеокарту, которой у VPS нет.

## Потоки

```
                     ┌──────────── VPS (только сайт) ────────────┐
   браузер ──HTTPS───┤ nginx → uvicorn/Django → Postgres, Redis  │
        │            │  • подписывает ссылки на PUT/GET в R2      │
        │            │  • ведёт очередь заданий                   │
        │            │  • проверяет манифест по спеке             │
        │            └───────────────┬───────────────────────────┘
        │                            │ (только подписи и метаданные,
        │                            │  байты сюда не заходят)
        │  прямой PUT                ▼
        └──────────────────────► Cloudflare R2 ◄──────── PUT готового
                                      ▲                  (пекарня)
                                      │ GET исходника
                       ┌──────────────┴──────────────┐
                       │  ПЕКАРНЯ — любая машина     │
                       │  с видеокартой и интернетом │
                       │  ffmpeg + NVENC, tools/bake │
                       └─────────────────────────────┘
```

Пекарня — **обычный клиент**, а не сервер. Нужен только исходящий интернет: белого
адреса, проброса портов и постоянной работы не требуется. Отсюда главное следствие:
факультетский сервер с видеокартой падает — тот же скрипт запускается на домашнем
компьютере и доделывает очередь. Это не запасной путь, а штатный.

## Спека форматов

Одно место, где записано, что считается готовым файлом. Живёт на сайте и **отдаётся
наружу** ручкой `GET /intake/spec/` — пекарня читает рецепт у сайта, поэтому рецепт
существует в одном экземпляре и не может разъехаться между машинами.

| вид | контейнер | требования |
|---|---|---|
| `cosmetic-header` | mp4 / h264 | 1536×256, ≤ 8 с, ≤ 2 МБ, без звука, faststart, + постер |
| `cosmetic-background` | mp4 / h264 | 1920×1080, ≤ 8 с, ≤ 4 МБ, без звука, faststart, + постер |
| `lecture` | HLS | h264 + aac, дорожки 1080/720/480, сегменты 4–6 с, + постер, + длительность |

### Почему faststart обязателен

`moov` — оглавление файла: таблицы сэмплов, метки времени, смещения. Пока его нет,
плеер не знает, где начинается картинка. `-movflags +faststart` переносит его вперёд;
без флага ffmpeg кладёт в конец, потому что до конца кодирования не знает итоговых
смещений.

Играть такой файл всё же можно: браузер догадается дозапросить хвост по `Range`,
и наша раздача `Range` умеет (`slice` в `nginx-files.conf`). То есть «не начнёт играть,
пока не скачает целиком» — неправда, и в тексте отказа этого больше нет.

Обязателен он по трём причинам, и все три про цену, а не про возможность:

1. Лишний круг до первого кадра. У нас он дорогой: nginx нарезает upstream ломтями
   по 1 МБ, и ради четырёх килобайт индекса тянется целый ломоть с другого конца файла.
2. На лекции это уже не мелочь: там `moov` весит мегабайты, и до первого кадра
   уходит вся дорога до конца файла и обратно.
3. Починка стоит ноль: это **ремукс**, перекладывание коробок без перекодирования
   картинки. Секунда на файл, качество то же самое.

Ошибка при этом не видна тому, кто грузил (у него файл в кеше и рядом) — её замечают
студенты на телефоне. **Первый же присланный образец был именно такой**: `mdat` на
36-м байте, `moov` в самом конце. Приёмка его отвергла.

Косметика без звука намеренно: это фон под текстом, звук там был бы издевательством.

### Чем печь косметику руками

```
ffmpeg -i source.mov -an -t 8 -vf "scale=1920:1080" \
       -c:v libx264 -profile:v high -pix_fmt yuv420p -crf 23 \
       -movflags +faststart fon.mp4
```

`-an` убирает звук, `-t 8` режет до восьми секунд, `-movflags +faststart` переносит
оглавление вперёд. На машине с видеокартой `-c:v h264_nvenc` вместо `libx264` —
быстрее в десятки раз.

**Постер — первым кадром того же видео**, и это не украшение:

```
ffmpeg -i fon.mp4 -frames:v 1 poster.png
```

Постер виден в те доли секунды, пока видео не готово, и в витрине — до подстановки
источника по видимости. Возьми чужую картинку, и на загрузке страницы будет скачок:
сперва одно, потом другое. Проверить это машиной нечем (кадр из видео от любой другой
картинки не отличить), поэтому правило живёт здесь и в `help_text` у поля.

Уже готовый ремукс без перекодирования, если файл хорош всем, кроме порядка коробок:

```
ffmpeg -i broken.mp4 -c copy -movflags +faststart fon.mp4
```

Образец лежит в `cosmetics/testdata/background.mp4` и на нём же держится тест разбора
заголовка: синтетика проверяет случаи по одному, а этот файл пришёл из жизни.

## Приёмка на сайте

Ручки под токеном (`INTAKE_TOKEN` в `.env` сервера):

| ручка | что делает |
|---|---|
| `GET /intake/spec/` | текущая спека, JSON. Читает пекарня |
| `POST /intake/claim/` | взять следующее задание: в ответ подписанный GET на исходник и id задания |
| `POST /intake/plan/` | манифест результата → сверка со спекой → ключи и подписанные PUT |
| `POST /intake/commit/` | «залил» → сайт делает HEAD по ключам, привязывает файлы к записи, закрывает задание |

**Проверка без ffmpeg.** Сверка манифеста со спекой плюс чтение первых десятков
килобайт mp4: боксы `ftyp`, `moov`, `tkhd` дают контейнер, кодек, разрешение и порядок
`moov`/`mdat`. Полсотни строк на чистом питоне — это разбор заголовка контейнера,
а не обработка видео.

## Пекарня (`tools/bake`)

Скрипт лежит в этом же репозитории — рядом с сайтом, чтобы рецепты и валидатор
правились одним коммитом, — но запускается только на машине с видеокартой.

Цикл:

1. `POST /intake/claim/` → задание или «пусто, спи дальше».
2. Скачать исходник по подписанной ссылке прямо из R2.
3. `ffmpeg` по рецепту из спеки. На видеокарте `h264_nvenc`: часовая лекция —
   минуты вместо часов. Для говорящей головы и слайдов качество NVENC неотличимо.
4. Проверить свой же результат через `ffprobe`, собрать манифест.
5. `POST /intake/plan/` → подписанные PUT → залить файлы **напрямую в R2**.
6. `POST /intake/commit/`.

Запускается и разово (`bake --once`), и демоном с опросом раз в N минут. Два
экземпляра на разных машинах не мешают друг другу: задание выдаётся ручкой `claim`,
а она атомарна на стороне базы.

**У пекарни нет ключей от R2.** Она получает подписанные ссылки от сайта — та же
`sign_upload`, которой уже пользуется форма загрузки материалов. Единственный секрет
на домашнем компьютере — токен приёмки, и его можно отозвать одной правкой `.env`.

> Это единственное место, где реализация отличается от первоначального наброска
> «пекарня опрашивает бакет напрямую». Причина: опрос бакета требует ключей R2 на
> каждой машине, где запускается скрипт, и не даёт атомарного захвата задания — две
> машины взяли бы одну лекцию. Свойство «нужен только исходящий интернет» при этом
> сохраняется полностью: все запросы инициирует пекарня.

## Сырьё: как лекция попадает в облако

Несжатая запись уходит в R2 **прямой загрузкой из браузера**, мимо сервера сайта.
Механизм уже работает и используется формой материалов (`attachments/uploads.py`):
сервер сам выбирает ключ и подписывает его, браузер кладёт файл по временной ссылке.

Сайт при этом знает о загрузке (он же выдавал подпись) и заводит задание со статусом
«ждёт обработки». Поэтому сдать лекцию может любой, у кого есть право, — видеокарта
и доступ к чужим машинам ему не нужны.

## Раздача

Готовые файлы раздаются существующим способом: `files.inbicst.ru` → Django проверяет
подпись → `X-Accel-Redirect` → nginx берёт из своего кеша или один раз из R2. Байты
через python не идут.

Единственное новое звено — **HLS**. Плейлист `.m3u8` ссылается на сегменты
относительными именами, а у нас все адреса подписанные. Решение: Django генерирует
плейлист на лету, подставляя подписанные адреса сегментов. Файл текстовый и
крошечный, а свойство «по бакету не походишь» сохраняется. Сегменты идут тем же
`X-Accel-Redirect` и так же кешируются.

**Почему HLS, а не один большой mp4.** Одиночный PUT упирается в 4 ГБ
(`MAX_DIRECT_SIZE`), дальше нужен multipart — он висит в коде как TODO. Сегменты
по несколько мегабайт снимают потолок вообще, и этот TODO можно не делать никогда.
Плюс адаптивное качество на плохом вайфае.

## Косметика: тот же договор, короткий путь

Фон и шапка весят 1–4 МБ, поэтому пекарня им не обязательна: файл печётся руками по
документированной команде и перетаскивается в админку. Работает **тот же валидатор**
и отказывает точной формулировкой вида «ждали 1536×256, приехало 1920×1080».

Одна спека, один валидатор, два способа доставки.

## Хранение анимации в моделях

Развилка проходит по прозрачности:

| вещь | альфа | формат |
|---|---|---|
| рамка аватара | нужна (проём под лицо) | остаётся APNG |
| шапка профиля | не нужна | mp4 |
| фон профиля | не нужна | mp4 |

Прозрачного видео, работающего везде, не существует: VP9 умеет альфу, но Safari её
не декодирует; HEVC с альфой умеет только Safari. Ради картинки 224×224 это не
окупается.

В модели `CosmeticItem` добавляется **одно поле** `video` (необязательное). Поле
`image` остаётся и означает «как вещь выглядит картинкой»: для рамки это сама
APNG-анимация, для фона и шапки — постер. Правило отрисовки одно и в одном месте:
есть `video` — рисуем `<video autoplay muted loop playsinline poster=image>`,
нет — `<img>`.

`playsinline` обязателен, иначе iOS открывает видео на весь экран.

Формат только mp4/h264 — играет везде, включая iOS. Стим держит ещё и webm, потому
что тот на 15% легче, но при их трафике; нам второй файл на каждую вещь не окупается.

**В витрине видео подгружается по попаданию в экран** (IntersectionObserver), а не по
наведению. Причина не в трафике: Safari на телефоне держит ограниченное число
одновременных видеодекодеров, и два десятка автоплеев его уронят.

## Замеры, на которых стоят решения

- Все 49 анимаций косметики — **34.7 МБ**, медиана 295 КБ, но 8 тяжёлых рамок дают
  57% веса (худшая — «Аганим», 4.93 МБ на 150 кадров).
- Перекодировка APNG в анимированный WebP: 192px q85 — всего **×0.62**, и при этом
  лоссИ. Второй формат ради 38% не заводим.
- Стим для анимированных фонов отдаёт пару webm + mp4 и постер: замеренный пример —
  mp4 3.9 МБ, webm 3.2 МБ, постер 126 КБ. Разметка — `<video autoplay loop muted
  poster>` с **пустым `src`**, источник подставляется скриптом при попадании в экран.
  То есть схема «постер + видео + ленивая подстановка» подсмотрена, а не выдумана.
- `imageio-ffmpeg` ставится обычным pip (колесо 31 МБ, статический бинарник, без apt
  и sudo). Нужен **только на пекарне**; на сайте его нет.

## Решения пользователя, которые из кода не выводятся

- Карточки профиля делаем **полупрозрачными**, иначе фона не видно с телефона:
  колонка занимает всю ширину и полей по бокам нет.
- Поверх фона в **светлой теме** кладём вуаль под цвет темы — иначе тёмный фон
  на всю ширину ломает настроение светлой страницы.
- Токены за прошлые заслуги на проде **уже розданы**, разовая процедура больше
  не поддерживается (`recount_tokens --reset` вырезан).
- Мерч — **отдельная страница**, товары за рубли, заказ уходит сообщением в
  телеграм-чат ответственных, дальше живые люди. Делается после косметики.
