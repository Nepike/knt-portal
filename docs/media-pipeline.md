# Конвейер тяжёлой медиа: пекарня и приёмка

Договор о том, как на сайт попадают видеофайлы — фоны профиля, шапки и лекции.
Решено 25 авг 2026. **Заменяет** ту часть `PLAN.md`, где GPU-воркер сидел на WireGuard
и слушал очередь Celery: воркер больше не сервер, ему не нужен ни белый адрес, ни
входящий доступ.

## Принцип

> **Сайт не конвертирует. Сайт принимает по спеке и отказывает с внятной причиной.**

На сервере-хостинге нет и не будет `ffmpeg`. Он отдаёт страницы, ведёт базу и раздаёт
ссылки; байты видео не проходят через python ни на загрузке, ни на раздаче.

Три причины: перекодировка часовой лекции займёт часы и положит машину, которая
одновременно обслуживает 500 человек; тяжёлая зависимость в образе не нужна ради
операции, случающейся раз в неделю; а качество и скорость всё равно упираются
в видеокарту, которой у VPS нет.

## Потоки

```
                     ┌──────────── VPS (только сайт) ────────────┐
   браузер ──HTTPS───┤ nginx → uvicorn/Django → Postgres, Redis  │
        │            │  • подписывает ссылки на PUT/GET в R2      │
        │            │  • ведёт очередь заданий                   │
        │            │  • проверяет манифест по спеке             │
        │            └───────────────┬───────────────────────────┘
        │                            │ (только подписи и метаданные,
        │                            │  байты сюда не заходят)
        │  прямой PUT                ▼
        └──────────────────────► Cloudflare R2 ◄──────── PUT готового
                                      ▲                  (пекарня)
                                      │ GET исходника
                       ┌──────────────┴──────────────┐
                       │  ПЕКАРНЯ — любая машина     │
                       │  с видеокартой и интернетом │
                       │  ffmpeg + NVENC, tools/bake │
                       └─────────────────────────────┘
```

Пекарня — **обычный клиент**, а не сервер. Нужен только исходящий интернет: белого
адреса, проброса портов и постоянной работы не требуется. Отсюда главное следствие:
факультетский сервер с видеокартой падает — тот же скрипт запускается на домашнем
компьютере и доделывает очередь. Это не запасной путь, а штатный.

## Спека форматов

Одно место, где записано, что считается готовым файлом: `intake/spec.py`. Отдаётся
**наружу** ручкой `GET /intake/spec/` — пекарня читает требования у сайта, а не помнит
свои: её копия репозитория может быть недельной давности.

Готовое бывает двух видов, и мерки у них разные:

| вид | форма | требования |
|---|---|---|
| `cosmetic-header` | `Clip` | mp4/h264, 1536×256, ≤ 8 с, ≤ 2 МБ, без звука, faststart, + постер |
| `cosmetic-background` | `Clip` | mp4/h264, 1920×1080, ≤ 8 с, ≤ 8 МБ, без звука, faststart, + постер |
| `lecture` | `Ladder` | HLS fMP4, h264 + aac, ступени 1080/720, сегменты 6 с, ≤ 30 к/с, + обложка |

`Clip` — один короткий файл целиком, и меряется он точно: размер, длина, вес.
`Ladder` — набор HLS, где одним числом ничего не измеришь: несколько дорожек, тысячи
сегментов, манифесты. У него сверяется **описание набора**, а не файлы — открыть их все
не может ни сайт, ни пекарня. Зато число сегментов обязано сходиться с длительностью,
и на этом ловится оборванная выпечка: снаружи полулекция выглядит совершенно целой.

Размер у видео сверяется **точно**, а не пропорцией: файл печётся с нуля по этой же
строке, и промахнуться мимо неё можно только ошибкой. У картинок мерка мягче — пропорция
и минимальная ширина (`cosmetics/specs.py`): полсотни рамок достались со старого сайта
разнокалиберными, и переделать их некому.

`heights` у лесенки — это **потолок, а не список обязательных дорожек**. Вверх не
растягиваем никогда: из записи 720p дорожка 1080p не появится, выйдет тот же кадр
крупнее и вдвое тяжелее. Запись ниже нижней ступени берём как есть, одной дорожкой —
лекция в 480p лучше, чем никакой.

Сверяют `spec.check` и `spec.check_ladder`, и их же зовёт пекарня перед отправкой.
Поэтому «прошло у меня» и «приняли на сайте» — буквально одна проверка, а не две похожие.

**Команду ffmpeg сайт наружу не отдаёт**, хотя в первом наброске рецепт был вместе
с ней. Исполнять командную строку, присланную по сети, — плохая форма даже когда сеть
своя, а кодек всё равно выбирается на месте (есть NVENC — им, нет — libx264). Один
экземпляр нужен ТРЕБОВАНИЯМ; способ их достичь — дело пекарни.

### Почему faststart обязателен

`moov` — оглавление файла: таблицы сэмплов, метки времени, смещения. Пока его нет,
плеер не знает, где начинается картинка. `-movflags +faststart` переносит его вперёд;
без флага ffmpeg кладёт в конец, потому что до конца кодирования не знает итоговых
смещений.

Играть такой файл всё же можно: браузер догадается дозапросить хвост по `Range`,
и наша раздача `Range` умеет (`slice` в `nginx-files.conf`). То есть «не начнёт играть,
пока не скачает целиком» — неправда, и в тексте отказа этого больше нет.

Обязателен он по трём причинам, и все три про цену, а не про возможность:

1. Лишний круг до первого кадра. У нас он дорогой: nginx нарезает upstream ломтями
   по 1 МБ, и ради четырёх килобайт индекса тянется целый ломоть с другого конца файла.
2. На лекции это уже не мелочь: там `moov` весит мегабайты, и до первого кадра
   уходит вся дорога до конца файла и обратно.
3. Починка стоит ноль: это **ремукс**, перекладывание коробок без перекодирования
   картинки. Секунда на файл, качество то же самое.

Ошибка при этом не видна тому, кто грузил (у него файл в кеше и рядом) — её замечают
студенты на телефоне. **Первый же присланный образец был именно такой**: `mdat` на
36-м байте, `moov` в самом конце. Приёмка его отвергла.

Косметика без звука намеренно: это фон под текстом, звук там был бы издевательством.

### Чем печь косметику

```
python tools/bake.py background zakat.mov
```

Пекарня сама возьмёт требования, выберет кодировщик, впишет кадр, вынет постер
и проверит результат. Подробности — ниже, в разделе про неё.

Руками, если пекарни под рукой нет:

```
ffmpeg -i source.mov -an -t 8 \
       -vf "scale=1920:1080:force_original_aspect_ratio=increase,crop=1920:1080" \
       -c:v libx264 -profile:v high -pix_fmt yuv420p -crf 23 \
       -movflags +faststart fon.mp4
```

`-an` убирает звук, `-t 8` режет до восьми секунд, `-movflags +faststart` переносит
оглавление вперёд. На машине с видеокартой `-c:v h264_nvenc` вместо `libx264` —
быстрее в десятки раз.

**Вписываем с обрезкой, а не растягиванием.** Прежде здесь стоял голый
`scale=1920:1080`: исходник ровно 16:9 бывает не всегда, а ровно 6:1 не бывает почти
никогда, и шапка выходила расплющенной. `force_original_aspect_ratio=increase` плюс
`crop` кроют кадр целиком и срезают лишнее по краям.

**Постер — первым кадром того же видео**, и это не украшение:

```
ffmpeg -i fon.mp4 -frames:v 1 -q:v 3 poster.jpg
```

Постер виден в те доли секунды, пока видео не готово, и в витрине — до подстановки
источника по видимости. Возьми чужую картинку, и на загрузке страницы будет скачок:
сперва одно, потом другое. Проверить это машиной нечем (кадр из видео от любой другой
картинки не отличить), поэтому правило живёт здесь и в `help_text` у поля.

JPEG, а не PNG: постер качается на КАЖДОМ показе витрины, а видео — только у попавших
в экран, так что байт постера стоит дороже байта видео. Замер на одном и том же кадре
1920×1080 плотной картинки: JPEG `-q:v 3` — **123 КБ**, PNG — **745 КБ**, ровно в шесть
раз. Потолок записан в рецепте полем `poster_bytes`.

Уже готовый ремукс без перекодирования, если файл хорош всем, кроме порядка коробок:

```
ffmpeg -i broken.mp4 -c copy -movflags +faststart fon.mp4
```

Образец лежит в `intake/testdata/background.mp4` и на нём же держится тест разбора
заголовка: синтетика проверяет случаи по одному, а этот файл пришёл из жизни.

## Приёмка на сайте

Приложение `intake`. Ручки под токеном (`INTAKE_TOKEN` в `.env` сервера), заголовком
`Authorization: Bearer <токен>`: логин пекарне не годится, у неё нет ни браузера, ни
сессии. Пустой `INTAKE_TOKEN` — приёмка отвечает 503 и не пускает никого: ручки открыты
в интернет без логина, и забытая настройка не должна превращаться в открытую дверь.

| ручка | что делает |
|---|---|
| `GET /intake/spec/` | ✅ текущая спека, JSON. Читает пекарня |
| `POST /intake/claim/` | взять следующее задание: в ответ подписанный GET на исходник и id задания |
| `POST /intake/plan/` | манифест результата → сверка со спекой → ключи и подписанные PUT |
| `POST /intake/commit/` | «залил» → сайт делает HEAD по ключам, привязывает файлы к записи, закрывает задание |

**Проверка без ffmpeg.** Сверка манифеста со спекой плюс чтение первых десятков
килобайт mp4 (`intake/mp4.py`): боксы `ftyp`, `moov`, `tkhd` дают контейнер, кодек,
разрешение и порядок `moov`/`mdat`. Полсотни строк на чистом питоне — это разбор
заголовка контейнера, а не обработка видео.

`intake/spec.py` и `intake/mp4.py` **не импортируют Django**: их берёт с собой пекарня
на машину, где ни проекта, ни настроек нет. На это есть тест, запускающий их импорт
отдельным процессом, — иначе случайный `from django...` обнаружился бы уже на той
машине, у человека, который просто хотел испечь фон.

## Пекарня (`tools/bake.py`)

Скрипт лежит в этом же репозитории — рядом с сайтом, чтобы требования и валидатор
правились одним коммитом, — но запускается на машине с видеокартой. Написан
на **одной стандартной библиотеке**, без venv и pip: запускается везде, где просто есть
python, и единственная внешняя вещь — сам ffmpeg. Из проекта берутся ровно два модуля,
`intake.spec` и `intake.mp4`, оба намеренно без Django.

```
python tools/bake.py background zakat.mov
python tools/bake.py header polosa.mp4 -o готовое --cpu
```

Настройки — аргументом, переменной окружения или строкой в `.env` репозитория, в этом
порядке: `INTAKE_URL` и `INTAKE_TOKEN`. Ни того ни другого нет — печём по локальной
копии требований и говорим об этом вслух.

Что делает:

1. Спрашивает требования у сайта (`GET /intake/spec/`). Не ответил — предупреждает
   и берёт локальную копию: молча испечь по устаревшим требованиям хуже, чем не испечь.
2. Ищет ffmpeg на `PATH`, потом в колесе `imageio-ffmpeg`.
3. **Проверяет NVENC делом, а не списком `-encoders`**: там перечислено
   вкомпилированное, а работает оно только при живой карте и драйвере. Кодирует
   несколько чёрных кадров 256×256 — на 64×64 NVENC отвечает «Frame Dimension less
   than the minimum supported value», и проба врала бы, что видеокарты нет.
4. Печёт: вписывает кадр с обрезкой, режет по длине, убирает звук, выносит оглавление
   вперёд.
5. **Не влез в потолок веса — жмёт сильнее и пробует снова**, до трёх заходов.
   Иначе человек получал бы «тяжелее 8 МБ» и крутил бы ручки сам, а пекарня заведена
   ровно за этим. Замер на плотной картинке: 12.9 → 8.5 → 5.3 МБ, весь заход 3 секунды.
   TODO (лекторий): часовой лекции три полных прохода не подходят — там нужен расчёт
   битрейта от длительности, а не лесенка.
6. Вынимает постер первым кадром **готового файла** и проверяет пару той же
   `spec.check`, которой их встретит сайт.

Файлы называются `<исходник>-<рецепт>.mp4`: без рецепта в имени шапка и фон из одного
исходника оба звались бы одинаково, и второй молча затирал бы первый.

**NVENC при том же числе качества даёт файл заметно тяжелее**, чем libx264: замер на
одном исходнике — `-crf 23` у libx264 дал 5.1 МБ, `-cq 23` у NVENC 10.4 МБ. Стартовое
число всё равно оставлено общим: на настоящем видео (не синтетике из замера) в потолок
попадает первый заход, а занижать качество заранее ради редкого лишнего прохода
неправильно — лишний проход стоит секунду.

### Как печётся лекция

```
python tools/bake.py lecture zapis.mkv
```

Кладёт папку с мастер-манифестом, дорожками, обложкой и `manifest.json` — описанием
готового, тем самым, которое потом уедет в `POST /intake/plan/`.

**Обе дорожки за одно декодирование.** Фильтр `split` разветвляет очищенный кадр на
две ветки, и ffmpeg запускается один раз. Отдельным запуском на дорожку файл
декодировался бы и чистился заново, а чистка тут самое дорогое: на замере два прохода
стоили ровно вдвое дольше одного со `split`.

**Обложка — кадр на десятой части записи**, а не первый. У косметики постер обязан
совпадать с первым кадром своего же видео, иначе на загрузке виден скачок; у лекции это
картинка в списке, и пустая доска первой секунды в ней бесполезна.

**Частота кадров режется до 30, но никогда не поднимается.** Поднять значило бы
дорисовать кадры из ничего.

Две грабли, на которых это ловилось делом, обе видны только на windows-пекарне:

* Пути в ffmpeg передаются **через `as_posix()`**. Имена из шаблонов ffmpeg кладёт
  в манифест как есть, а там это URL: с windows-путём в мастер уезжало `0\index.m3u8`,
  и набор не заиграл бы нигде. От той же обратной косой ломался вывод init-сегмента —
  он не создавался вовсе, и набор выходил правдоподобным и мёртвым.
* NVENC нужен **`-forced-idr 1`**. Без него на местах из `-force_key_frames` он ставит
  обычные опорные кадры вместо IDR, резать по ним HLS нельзя, и сегменты выходят
  длиннее заказанных — 7.7 с вместо 6.

Обе поймала самопроверка: она разбирает манифесты, а не смотрит на список файлов
в папке, и видит набор ровно так, как увидит сайт.

### Замеры на настоящей записи

Кусок лекции: доска, камера чуть плывёт, 1920×1080, **60 к/с, 17.8 Мбит/с** — то есть
два часа такого весят **≈ 16 ГБ**. Битрейт для пустой доски абсурдный, это неверно
настроенный OBS; исправить настройки записи — самый дешёвый выигрыш во всей затее,
но рассчитывать на это нельзя, и система обязана принимать и такое.

Шумоподавление на этой картинке решает больше всего: шум матрицы на плоской зелёной
поверхности съедает биты, а дрейф камеры не даёт выиграть на статичной сцене.

| шумодав | 1080p | 720p | вместе | 2 часа |
|---|---|---|---|---|
| без чистки | 3.60 | 1.19 | 4.79 Мбит/с | 4.01 ГБ |
| **мягко `1:2:3:5`** | 2.74 | 0.84 | **3.58 Мбит/с** | **3.00 ГБ** |
| жёстко `3:3:6:6` | 1.90 | 0.66 | 2.56 Мбит/с | 2.15 ГБ |

По умолчанию стоит **мягкая**. Первое число — пространственная чистка яркости, ровно
она и размывала бы тонкие штрихи мела; экономию дают временнáя и цветовая, которым мел
безразличен. Проверить на исписанной доске пока не на чем — присланный кусок пустой, —
поэтому выбрана осторожная настройка ценой 40% лишнего места. Появится запись с мелом —
сравнить и, если штрихи держатся, перейти на жёсткую. Снять совсем: `--denoise none`.

Выпечка ста секунд заняла 17 с, то есть **два часа ≈ 20 минут** на RTX 5060 Ti,
и это сразу обе дорожки. Сегментов на двухчасовую лекцию ≈ 2400.

### Очередь заданий

```
python tools/bake.py --serve          # ждать работы
python tools/bake.py --once           # взять одно задание и выйти
```

Пекарня приходит сама — сервером она не работает, белого адреса ей не нужно. Цикл:
`claim` → скачать сырьё по подписанной ссылке → испечь → `plan` → `sign` → залить куски
напрямую в хранилище → `commit`. Не вышло — `fail` с причиной, и человек видит на
странице, что запись не обработалась, а не вечное «обрабатывается».

| ручка | что делает |
|---|---|
| `POST /intake/claim/` | взять задание: подписанная ссылка на сырьё и токен задания |
| `POST /intake/plan/` | манифест → сверка со спекой → папка, куда класть |
| `POST /intake/sign/` | подписанные ссылки на очередную порцию кусков |
| `POST /intake/commit/` | «залил» → сайт проверяет полноту и привязывает к лекции |
| `POST /intake/fail/` | не вышло, вот причина |

* **Задание выдаётся ровно одной машине.** `select_for_update(skip_locked=True)`: две
  пекарни, пришедшие разом, не получат одну лекцию — вторая пропустит занятую строку
  и возьмёт следующую, а не встанет ждать.
* **Брошенное возвращается в очередь** через час молчания. Иначе упавшая машина
  заморозила бы лекцию навсегда.
* **Манифест сверяется ДО заливки.** Отвергнуть описание дешевле, чем принять две
  тысячи кусков и обнаружить, что дорожка не та.
* **На `commit` считаются ключи под папкой**, а не спрашивается про каждый: их тысячи.
  Без этого оборванная заливка прошла бы незамеченной и лекция открылась бы наполовину.
* **Сырьё после сборки удаляется** — гигабайты, из которых уже всё взяли.
* Токен задания подписан: номер приходит от пекарни, и без подписи она закрыла бы чужое.

Проверено целиком на стенде с поддельным бакетом: настоящая запись, настоящий ffmpeg,
пекарня отдельным процессом — задание взято, сырьё скачано, обе дорожки испечены,
41 кусок залит, задание закрыто, у лекции появились папка и длительность.

**У пекарни нет ключей от R2.** Она получает подписанные ссылки от сайта — та же
`sign_upload`, которой уже пользуется форма загрузки материалов. Единственный секрет
на домашнем компьютере — токен приёмки, и его можно отозвать одной правкой `.env`.

> Это единственное место, где реализация отличается от первоначального наброска
> «пекарня опрашивает бакет напрямую». Причина: опрос бакета требует ключей R2 на
> каждой машине, где запускается скрипт, и не даёт атомарного захвата задания — две
> машины взяли бы одну лекцию. Свойство «нужен только исходящий интернет» при этом
> сохраняется полностью: все запросы инициирует пекарня.

## Сырьё: как лекция попадает в облако

Несжатая запись уходит в R2 **прямой загрузкой из браузера**, мимо сервера сайта.
Механизм уже работает и используется формой материалов (`attachments/uploads.py`):
сервер сам выбирает ключ и подписывает его, браузер кладёт файл по временной ссылке.

Сайт при этом знает о загрузке (он же выдавал подпись) и заводит задание со статусом
«ждёт обработки». Поэтому сдать лекцию может любой, у кого есть право, — видеокарта
и доступ к чужим машинам ему не нужны.

## Раздача

Готовые файлы раздаются существующим способом: `files.inbicst.ru` → Django проверяет
подпись → `X-Accel-Redirect` → nginx берёт из своего кеша или один раз из R2. Байты
через python не идут.

Единственное новое звено — **HLS** (`attachments/hls.py`). Манифест `.m3u8` ссылается на
куски относительными именами, а у нас все адреса подписанные. Django переписывает его
на лету, подставляя подписанные адреса. Файл текстовый и крошечный, а свойство
«по бакету не походишь» сохраняется. Сегменты идут тем же `X-Accel-Redirect`.

Подробности, которые из кода видны не сразу:

* **Адрес есть и внутри тега**: `#EXT-X-MAP:URI="init_0.mp4"` — это init-кусок, без
  которого сегменты не декодируются вовсе. Переписывать только строки-имена мало.
* **`../` в манифесте отвергаем.** Подпись выдаётся на любой вычисленный ключ, и такое
  имя увело бы её на чужую лекцию. Манифесты печём мы сами — но это ровно то место, где
  «мы сами» однажды перестаёт быть правдой.
* **Своя соль у кусков HLS**, не общая с картинками: подпись — это разрешение, и
  разрешение на сегмент лекции не должно годиться там, где отдаются любые ключи.
* **Переписанный текст кешируется.** Содержимое куска неизменно (в ключе uuid,
  перезапись запрещена), подпись у нас без времени — значит и результат постоянен.
  Иначе каждый запуск плеера стоил бы похода в бакет и тысячи подписей.
* **CORS обязателен, и его ставит Django, а не nginx.** Картинку браузер берёт тегом,
  а `hls.js` — запросом из скрипта, и домен файлов для страницы чужой: без заголовка
  ответ приходит, но отдать его плееру браузер отказывается, и видео молча не заводится.
  Список разрешённых берём из `CSRF_TRUSTED_ORIGINS` — это ровно наши собственные
  адреса, а второй такой же список рано или поздно разошёлся бы с первым. При
  `X-Accel-Redirect` заголовок приложения побеждает, поэтому правка nginx не нужна.

**Плеер** — `lectorium/templates/lectorium/_player.html` плюс компонент `lecturePlayer`.
Библиотеку (`hls.min.js` 1.6.15 в `core/static/core/vendor/`, как htmx и alpine) он
догружает сам по `data-library`: тег в шапке пришлось бы ставить ДО ядра Alpine, и
каждая страница с плеером была бы обязана про это помнить. **Без файла страница упадёт
на проде** пятисоткой — `ManifestStaticFilesStorage` не прощает ссылку на отсутствующий
файл; в разработке она отрисуется, а плеер честно скажет, что не загрузился.

Обрыв сети и сбой декодера плеер переживает трижды, дальше просит обновить страницу:
без счётчика безнадёжный случай крутился бы в цикле, а лекцию смотрят час с лишним.

Три вещи, которые нашлись только в живом браузере:

* **Плеер держим в замыкании, а не в данных компонента.** Alpine оборачивает данные
  в `Proxy`, а hls.js разбирает поток в Worker и шлёт туда свои объекты через
  `postMessage` — прокси структурно не клонируется, и разбор падает сразу:
  «Failed to execute 'postMessage' on 'Worker': #<Object> could not be cloned».
  Ни тесты, ни чтение кода такое не ловят.
* **hls.js первым, родной HLS запасным.** Сперва было наоборот, из соображения «Safari
  играет сам и бережнее к батарее». Но `canPlayType` отвечает «maybe» и там, где своего
  HLS на деле нет, — поймали на движке хрома, — а родной плеер не умеет ни пережить
  обрыв, ни рассказать о нём. Теперь порядок как советует сама библиотека.
* **На айфоне библиотека не скачивается вовсе.** Наличие `MediaSource` проверяем ДО
  загрузки: в iOS её нет (там любой браузер — Safari внутри), hls.js бесполезен, и
  полмегабайта телефон тянул бы впустую. Там работает как раз запасная ветка.

**Почему HLS, а не один большой mp4.** Сегменты по несколько мегабайт снимают потолок
размера вообще, а на плохом вайфае дают адаптивное качество.

## Сырьё: многочастная загрузка

Готовое режется на сегменты само, а вот **исходник** — это единый файл на гигабайты,
и его надо как-то доставить. Одиночный PUT такого не принимает, но дело даже не в
потолке: 16 ГБ с домашнего канала — это больше получаса отдачи, и связь за это время
оборвётся почти наверняка. Начинать сначала человек не станет.

Поэтому загрузка **многочастная и возобновляемая**: файл режется на части по 16 МБ,
каждая подписывается отдельно, три льются разом. Оборвалась одна — повторяется она
одна, до четырёх попыток с растущей паузой. Закрылась вкладка — браузер помнит номер
начатой загрузки, а **что именно уже долетело, спрашивается у хранилища**: браузер мог
закрыться, потерять свою память или соврать, правду знает только бакет.

| ручка | что делает |
|---|---|
| `POST /files/upload/start/` | начать или продолжить: отдаёт токен, размер части и список уже залитых |
| `POST /files/upload/parts/` | подписанные ссылки на очередную порцию частей |
| `POST /files/upload/finish/` | собрать объект и вернуть токен — тот же, что после обычной загрузки |
| `POST /files/upload/abort/` | бросить начатое |

Подробности, которые из кода видны не сразу:

* **В CORS бакета обязателен `ExposeHeaders: ETag`.** ETag части — это расписка, без
  которой объект не собрать; заголовок приходит всегда, но ЧИТАТЬ его скрипту браузер
  даёт только с этого разрешения. Забыть — значит залить гигабайты и споткнуться на
  последнем шаге, поэтому клиент отвечает на это прямым текстом, а не «ошибкой».
* **Токен подписан.** Ключ и номер загрузки приходят от браузера: без подписи он мог бы
  дописаться в чужую загрузку или собрать объект по чужому ключу.
* **Мёртвый номер не переиспользуем.** Загрузку могли отменить, а браузер держит токен;
  сайт спрашивает хранилище и, если такой загрузки нет, начинает заново. Иначе человек
  залил бы гигабайты в никуда и узнал об этом на самом последнем шаге.
* **Потолок размера — по праву.** Лекции нужны десятки гигабайт (`MAX_LECTURE_SIZE`),
  остальным хватает четырёх (`MAX_DIRECT_SIZE`): место в бакете стоит денег, а материалов
  такого размера не бывает. Различает их право `lectorium.add_playlist`.
* **Брошенное убирается.** Части начатой и не собранной загрузки лежат в бакете, но
  объектом не стали — обычным обходом каталога их не видно вовсе. Их снимает
  `manage.py clean_uploads`, отдельным запросом к списку многочастных загрузок.

Проверено на стенде с поддельным бакетом: при пяти отвергнутых частях файл всё равно
доехал целым, возобновление подхватило уже залитое.

## Косметика: тот же договор, короткий путь

Фон и шапка весят 1–4 МБ, поэтому пекарня им не обязательна: файл печётся руками по
документированной команде и перетаскивается в админку. Работает **тот же валидатор**
и отказывает точной формулировкой вида «ждали 1536×256, приехало 1920×1080».

Одна спека, один валидатор, два способа доставки.

## Хранение анимации в моделях

Развилка проходит по прозрачности:

| вещь | альфа | формат |
|---|---|---|
| рамка аватара | нужна (проём под лицо) | остаётся APNG |
| шапка профиля | не нужна | mp4 |
| фон профиля | не нужна | mp4 |

Прозрачного видео, работающего везде, не существует: VP9 умеет альфу, но Safari её
не декодирует; HEVC с альфой умеет только Safari. Ради картинки 224×224 это не
окупается.

В модели `CosmeticItem` добавляется **одно поле** `video` (необязательное). Поле
`image` остаётся и означает «как вещь выглядит картинкой»: для рамки это сама
APNG-анимация, для фона и шапки — постер. Правило отрисовки одно и в одном месте:
есть `video` — рисуем `<video autoplay muted loop playsinline poster=image>`,
нет — `<img>`.

`playsinline` обязателен, иначе iOS открывает видео на весь экран.

Формат только mp4/h264 — играет везде, включая iOS. Стим держит ещё и webm, потому
что тот на 15% легче, но при их трафике; нам второй файл на каждую вещь не окупается.

**В витрине видео подгружается по попаданию в экран** (IntersectionObserver), а не по
наведению. Причина не в трафике: Safari на телефоне держит ограниченное число
одновременных видеодекодеров, и два десятка автоплеев его уронят.

## Замеры, на которых стоят решения

- Все 49 анимаций косметики — **34.7 МБ**, медиана 295 КБ, но 8 тяжёлых рамок дают
  57% веса (худшая — «Аганим», 4.93 МБ на 150 кадров).
- Перекодировка APNG в анимированный WebP: 192px q85 — всего **×0.62**, и при этом
  лоссИ. Второй формат ради 38% не заводим.
- Стим для анимированных фонов отдаёт пару webm + mp4 и постер: замеренный пример —
  mp4 3.9 МБ, webm 3.2 МБ, постер 126 КБ. Разметка — `<video autoplay loop muted
  poster>` с **пустым `src`**, источник подставляется скриптом при попадании в экран.
  То есть схема «постер + видео + ленивая подстановка» подсмотрена, а не выдумана.
- `imageio-ffmpeg` ставится обычным pip (колесо 31 МБ, статический бинарник, без apt
  и sudo). Нужен **только на пекарне**; на сайте его нет.

## Лекторий: решения пользователя

Приняты 26 авг 2026, из кода не выводятся.

**Единица — плейлист, а не лекция.** Предмет, семестры и преподаватели висят на
плейлисте, лекция знает только своё место в нём. Отсюда и **обязательная** привязка:
на модерацию поступает плейлист с лекциями (как материал с файлами), значит плейлист
и есть модерируемая единица, а лекция без него оказалась бы вне проверки и без
метаданных вовсе. Одиночная запись оформляется плейлистом из одной лекции — так
устроены все видеосайты, и это одно лишнее поле в форме.

**Две ступени, не три.** Место дороже промежуточного качества.

**Заводить плейлисты — по отдельному праву Django**, как регистрация у старост.

**Модерация после выпечки, а не до.** Сырьё модерировать нельзя: `.mkv` из OBS
в браузере может просто не открыться. Значит загрузили → испекли → готово → проверка →
опубликовано. Впустую сожжённое время видеокарты — приемлемая цена, право загружать
будет не у всех.

Открытым осталось: возвращать ли **весь** плейлист на проверку при добавлении лекции
в уже опубликованный. У материалов правка возвращает; для курса из двадцати лекций
это может оказаться неудобно. Решать, когда дойдём.

В коде `Playlist` — только модель раздела. Манифесты HLS всюду зовутся **манифестами**,
и словом «плейлист» их не называем: спутать `Playlist` с `master.m3u8` слишком легко.

### Как устроен раздел

Лекция хранит **префикс папки**, а не файлы: набор — это манифесты, обложка и тысячи
сегментов, полем `FileField` такое не описать. Имена внутри папки известны заранее
(`intake.spec.MASTER`, `POSTER`) — их пишет пекарня, по ним сайт и находит набор.
Префикс уникален: две лекции на одной папке означали бы, что удаление первой уносит
файлы второй.

**Уборка при удалении — своя.** `post_delete` в `attachments` снимает только файловые
ПОЛЯ, а тут их нет. `attachments.storage.drop_prefix` снимает всё под префиксом:
у бакета пакетами по тысяче ключей (поштучно у двухчасовой лекции это 2400 запросов),
на диске ещё и опустевшие каталоги. Через очередь и только `on_commit` — удаление
файлов необратимо, а транзакция ещё может откатиться.

## Решения пользователя, которые из кода не выводятся

- Карточки профиля делаем **полупрозрачными**, иначе фона не видно с телефона:
  колонка занимает всю ширину и полей по бокам нет.
- Поверх фона в **светлой теме** кладём вуаль под цвет темы — иначе тёмный фон
  на всю ширину ломает настроение светлой страницы.
- Токены за прошлые заслуги на проде **уже розданы**, разовая процедура больше
  не поддерживается (`recount_tokens --reset` вырезан).
- Мерч — **отдельная страница**, товары за рубли, заказ уходит сообщением в
  телеграм-чат ответственных, дальше живые люди. Делается после косметики.
